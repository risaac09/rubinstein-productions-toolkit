# Resolve traps

> **Status:** operational 2026-11-09. Measured in DaVinci Resolve Studio 21.2, on scripted ` [auto]` timelines in a sandbox project. Each entry says what was seen and what works instead. An entry marked "not tested" is a claim from the scripting docs that nobody here has run. A live check on 2026-11-11, on the same build in the same sandbox, added or corrected the entries that say so; an item there that needed a rendered file stays "not tested live" until someone reads the render.

Other docs cite these by number (`T3`). A number never changes; a corrected trap keeps its number and says what replaced it.

## Timelines and items

- **T1. `AppendToTimeline` clip info.** `endFrame` is exclusive. An item's length is floor((end - start) x timeline fps / source fps). To get n timeline frames, ask for ceil(n x source fps / timeline fps) source frames.
- **T2. Frame rate.** A scripted timeline takes the project frame rate. `SetSetting("timelineFrameRate")` returns False once the timeline exists.
- **T8. Stills.** `ExportCurrentFrameAsStill` wants an absolute path and can return the previous frame. Seek a few frames early, seek to the frame, wait two seconds, then export. Wait longer after a timeline switch.
- **T10. Mixed rates.** `interchange` refuses a manifest whose sources mix 29.97 and 30 fps. It also wants every source at the timeline's rate. A 24 fps timeline from 29.97 or 60 fps sources is built by `assemble_timeline`, which appends each span at its clip's own rate (T1).
- **T12. Fill on a duplicated timeline.** A duplicated timeline set to 1080x1920 with `timelineInputResMismatchBehavior` = `scaleToCrop` reads the setting back and still renders every clip fitted to width. Set the item property `Scaling` to 3 on each item. Values: 0 project, 1 crop at native pixels, 2 fit, 3 fill, 4 stretch.
- **T18. A picture fade reads back; a music fade read back and did not render.** `TimelineItem.SetFades({"FadeIn": n, "FadeOut": n})` returns True on picture and audio items and `GetFades()` reads the frames back. A 12-frame fade-in was confirmed on a still: mean luma 6 at frame 1 against 24 at frame 40. On audio the read-back is all there is: eight masters built with a `SetFades` music fade out all ended on a hard cut (peaks of about -5 dBFS up to the last 50 ms on the meter), although Resolve's own scripting stub documents the call for audio items. The cause is not known. The read-back proves the property round-trips, not that the render fades. `assemble_timeline` therefore does not call it: it cuts the music with ffmpeg into a bed with a one second fade out baked into the file (`rpresolve/musicbed.py`: 24-bit 48 kHz WAV, never a fade over a quarter of the bed) and places that file on A1. `deliver_check` has a `tail` row for the rendered file (the 100 ms ending at the last video frame at least 12 dB below the window 3 s to 1.5 s before that frame), on for `social_9x16_music`. No tool sets a picture fade; a dip to black is the `dip-to-black` macro or a transition from `ui_steps`. This corrects T11. Live-tested 2026-11-11 on a rendered 16.6 s AAC mp4 of a build with the baked bed (`social_9x16_music`): `deliver_check` passed, 20 rows pass and 3 skipped (`fps_floor`, `video_bitrate`, `safe_zone`, no boxes given), loudness -13.7 LUFS, true peak -2.9 dBTP, and the `tail` row read "last 100 ms -79.2 dB, window -15.2 dB (64.0 dB lower)" against its 12 dB floor. That first version of the row overstated the fade: it measured the last 100 ms of the file with ffmpeg `-sseof`, which counts from the longest stream's end, and the container's audio ended 79 ms after the last frame, so that window was mostly codec padding and zeros. An independent decode put the last 100 ms of the audio 33 dB under the reference window, and the 100 ms ending at the picture's last frame 27 dB under it. A bed still at full level when the picture ended would have passed behind enough padding. The row now measures the 100 ms ending at the last video frame (the video stream's start_time plus its duration, `-ss` from the container's start instead of `-sseof`; when the stream carries no duration, as in an .mkv, the last video packet's end, read from the final 3 s of packets) and the reference window is counted back from the same frame; decoded audio length was not used, because it needs a full decode and still counts sound after the last frame, which no viewer sees. The 12 dB floor is unchanged: it was set from the baked fade (a one second linear fade ends about 25 dB down over those 100 ms) and not tuned to the padding. Tests with ffmpeg-made files whose audio runs 0.5 s past the picture pin it (a hard cut and a 50 ms fade fail, a one second fade passes). No render has been re-checked with the new window; a live check by the operator follows. The level fell 3 dB about 0.9 s before the end and 20 dB about 0.17 s before it, and the final 52 ms were exact zeros, so the baked fade rendered and the file has no hard cut. Read the row as pass or fail on a hard cut (which drops near 0 dB), not as the depth of the fade; the figures quoted here are from the first version of the row. The rendered audio ran 35 ms past the last frame when decoded and 79 ms in the container (AAC priming and 1024-sample frames); under two frames is expected, and the audio was not shorter than the picture. One render of one bed. The cause of the `SetFades` failure above is still unknown.
- **T11. Fade by menu (fallback).** Before T18 was measured, the working recipe was: make the timeline current on the Edit page, park the playhead where the fade starts, then Trim, Fade Out to Playhead from the menu bar. With nothing selected it fades only the clips under the playhead, so parking past the last picture frame fades the music alone. A timeline's FCPXML export does not carry fades, so there is no file read-back for either route.
- **T33. `get_image` draws only the current timeline.** `get_image` and `get_thumbnails` with source `timeline` draw whichever timeline is current in Resolve, and no tool of the resolve server makes a given timeline current and puts the old one back. The build and effect tools restore the current timeline, so a timeline they make is never current, and `queue_render` makes one current only around its own work. A call after a build therefore returns a frame of whatever the person has open: read the reply's `timeline=` field before reading a frame. Live-tested 2026-11-11 in four checks. To see a built timeline, ask the person to open it, or switch with the scripting API (`Project.SetCurrentTimeline`), read frames with `frame_offset` (counted from the timeline's first frame; the image header prints timecode 01:00:00:00 whatever the offset), and set the previous timeline current again, reading its name back to confirm. That changes what the person sees, so do it only when they have agreed. For the look of one clip, source `media_pool_clip` with the clip name and a `frame_offset` draws it colour managed with its own tags and no timeline grade, at the current timeline's shape (letterboxed when that is 9:16).

## Fusion on a timeline item

- **T3. Stale render.** A Fusion comp built by script passes its read-back and still renders the old picture. Toggling `TOOLB_PassThrough` on and then off on each added tool makes Resolve render it. `apply_effect` does this and checks it.
- **T4. Comp time.** Comp time on a timeline item counts source frames, with 0 at the item's first frame. A macro keyed over 48 frames lasts 48 source frames, which is 1.6 s of a 30 fps source on a 24 fps timeline. `apply_effect` scales a macro's key times by source frames over timeline frames. Checked on a still: a `TimeStretcher` keyed to half speed over a 90-source-frame item showed, 66 timeline frames in, the frame the source holds 1.375 s after the item's start.
- **T5. Retime.** `TimeSpeed` anchors on the clip's source frame 0, so it shows footage from far earlier in the file. A `TimeStretcher` with `SourceTime` keyed from 0 to speed x N does the retime correctly. This is the scripted stand-in for Edit page speed, ramps included.
- **T9. Deleting a comp.** `DeleteFusionCompByName` returned False on an item's only comp. Empty the comp and reuse it. `apply_effect` does: an item whose comps are all emptied `rp-fx` comps (only MediaIn1 and MediaOut1) is built into again, the comp loaded with `LoadFusionCompByName` and renamed, and the plan row says `reuse`. An item with a comp that holds tools, or any comp not named `rp-fx ...`, is still refused. Live-tested 2026-11-11 on Resolve 21.2.0.6 with the Deliver page open: `comp.GetToolList(False)` answers for a comp that is not open on the Fusion page, as a dict of {position: tool} whose tools carry `.Name` and `.ID`. A spline modifier is in it as a tool of its own (ID `BezierSpline`, named like `BrightnessContrast1Gain`), and `GetToolList(True)`, the selected-only form, returns an empty dict. `comp.FindTool(name).Delete()` works on such a comp with no Fusion page and no computer use, and it also removes the tool's animation spline, so a comp emptied this way reads exactly MediaIn1 and MediaOut1 and the reuse test accepts it. The comp stays on the item. A re-run of `apply_effect` then plans `reuse`, builds into it, and the result row says `reused`; a render of the item's last frame showed the new dip (mean luma 9.6 against 124.8 on its first frame), so the reused comp is the one that renders (T3). No MCP tool empties a comp: the check used the toolkit's own `api` module from a script, scoped to a test timeline.
- **T13. Spline handles.** The `RH` and `LH` handles in `SetKeyFrames` are offsets from their key. Absolute values overshoot.
- **T14. A pan that follows a subject.** A `Transform` on the item, `Center` given an `XYPath` modifier, a `BezierSpline` on its X keyed from 0.5 + c0 - start to 0.5 + c0 - end over the item's source frames. c0 is the crop centre the item's own Pan holds.
- **T22. Text+ fonts.** The family "Arial Black" set by script renders nothing. "Arial" with the style "Bold" works. Choose the real face in the Inspector.
- **T23. Gain is linear light.** In a colour-managed project a linear gain ramp from 1 to 0 looks like a late snap. Key a dip in even stops (1, 0.5, 0.25, 0.125, 0.06, 0.02, 0).
- **T24. Transitions are scriptable.** `TimelineItem.AddTransition({type: 'Cross Dissolve', category: 'simple', position: 'end', alignment: 'center', duration: n})` returns the transition item, or None when the cut has no handles. Read `GetDuration()` back: a short handle would shorten the dissolve without a word. Measured 2026-11-09: three 2-frame Cross Dissolves added on a 48-item timeline, each read back at 2 frames.
- **T25. A key before frame 0 gets a twin at 0.** When a spline's first keyframe is set at a negative comp frame (an end-anchored macro on an item shorter than the macro), Fusion adds a key at frame 0 with the curve's value there. Harmless to the picture; a read-back that counts keys must allow it. Measured 2026-11-10: `dip-to-black` on a 90-frame item (112 source frames) read keys at [-97, 0, 88, …, 111] for a macro moved to [-97, 88, …, 111]; gain sampled 1.0 through frame 88 and 0.0 at 111.
- **T26. A still is the source frame.** `Project.ExportCurrentFrameAsStill` writes the clip at its own size (3840×2160 from a 1080×1920 timeline), with the grade but without the timeline's size, Scaling or Pan. It cannot prove a 9:16 frame. Resolve's own MCP `get_image` with source `timeline` renders at the timeline's output size; a template match of that render inside the 16:9 still measured the window at the planned centre (cx 0.462 for 0.47 asked, correlation 0.998, 2026-11-10).
- **T28. A draft's flash was not the macro's.** The draft farm drew `exposure-flash` as an added brightness of 0.3; the macro multiplies by its gain in linear light (T23). On a bright day shot the two look alike; on a dark night shot the macro lifts mean luma from 49 to 65 where the old draft showed about 119, whatever the gain. Measured 2026-11-10 on a 5-frame item: gain 10 keyed to 1 over the macro's span matched that draft (117 on the first frame). A flash on an item shorter than its span never returns to normal inside the item, in the draft and the build alike. `apply_effect` takes `gain` (1 to 20, default 2) for `exposure-flash`: pass 10 to match a draft on a dark shot; a bright shot clips at any gain worth using (see the render below), so pass 2 only where white highlights are acceptable, and compare one rendered frame against the draft before committing a value. Judge a flash against an unflashed render of the same frame, never the item's first frame against its last. **Since 2026-11-10 one number serves both.** A fill's `gain` goes through `methods.to_manifest` as `params.gain` on the flash entry (a gain on any other slot is refused), `apply_effect` writes it into the macro, and the draft draws the same gain falling to 1 over 12 frames. **Since 2026-11-11 the draft draws the macro's own multiply.** It cannot do linear light, but a power-law display makes a linear gain a multiply of each channel by gain^(1/2.4) about video black, clipped at video white: `flash_filter` in `drafts.py` does that in planar RGB with `geq`, for the 12 frames of the fall only (`eq` cannot clip a channel). The first version (2026-11-10) multiplied luma alone by gain^(1/2.55), a gamma fitted on one flat dark frame (2.45 fitted the macro's 65 at gain 2, 2.64 its 117 at gain 10, and 2.55 drew 62 and 120) that never clipped; the dip still uses that fitted multiply on the macro's even-stop keys (T23), which no render has checked. A render checked the macro on 2026-11-11 on a dark, a bright and a V-Log shot under colour management, reading each flashed frame against the same frame of an unflashed twin (mean luma on the 16 to 235 video scale, full resolution, cross-checked with ffmpeg `signalstats`; channel-clip shares are approximate, rebuilt from the decoded YCbCr at 960x540). The macro is a plain gamma 2.4 multiply about video black: on the dark shot (unflashed 64) gain 2 read 81 and gain 10 read 141, against 81 and 142 from 16 + (luma - 16) x gain^(1/2.4). Peak lift over the unflashed frame: dark +16 at gain 2 and +77 at gain 10; bright (unflashed 159) +38 and +74; V-Log (unflashed 114) +28 and +90. The master clips hard at video white with no visible roll-off (Y never above 946 of 1023). On the bright shot gain 10 put 75 percent of the pixels at white in all three channels on the first frame (96 percent in at least one) and kept over half the frame at white for 8 frames; gain 2 put 18 percent at white and 47 percent in a clipped channel, and that unflashed shot already peaked within 2 percent of white. On the dark shot gain 2 clipped nothing and gain 10 clipped one channel in 9 percent of the pixels. A safe gain for a bright shot was not measured. The fall reached the unflashed picture on frame 12 on a 30 fps source and a frame later on two 29.97 fps sources (a residual of 2 to 4 levels on frame 12 at gain 10); with three shots the source rate is confounded with the shot, so that is an observation, not a finding. Drawn on the same unflashed frames, the luma-only draft's lift was within 4 levels of the build's at gain 2 and 7 to 17 levels off at gain 10: low on the dark shot (70 against 77) and high on the bright and V-Log shots (91 against 74, 102 against 90) because it did not clip at white and kept colour where the build goes white (bright, gain 10: 9 percent of pixels white in all channels in the draft, 75 percent in the build). That is what the per-channel clip fixes. The build read 81 and 141 to 142 on the dark shot at gains 2 and 10; the new draw, rendered on a flat frame of that level (video 64, no look, no colour management), reads 80.4 and 141.4, and a test holds it to 81 and 141.5 within 1.5, and the test on a 0 to 255 ramp holds every level to the formula within 1.2 times the multiplier plus 1.5, because the input's own 8-bit step is multiplied by the gain (the worst ramp readings were 2.8 at gain 2, 4.0 at 10 and 4.5 at 20). The shape of the fall was not re-fitted: the draft's smoothstep gives about +50 (49.8) at frame 6 of gain 10 on that flat frame where the build read +53. Run on the raw source frames, as a draft is, the unflashed bases read 43, 147 and 102 against the build's 64, 159 and 114, so colour management lifts the picture by 12 to 22 levels and a draft's absolute levels never match the build's (one run, not independently reproduced). An earlier offline per-channel model (bright frame, mean luma about 145) under-called the render: it predicted 179 at gain 2 and 224 at gain 10 with a little over half the frame white, and the render read 197 and 233 with 75 percent white; the earlier agreement between the draft and that model was not a draft-against-build comparison. Not measured: gains between 2 and 10, a look graded before the flash, a viewed frame (these are numbers only), and the new draw rendered against the build on real footage (the tests check it against the formula, not the build; a live check by the operator follows). The draft draws a V-Log source flat (no look cube), so its flash cannot be compared with a colour-managed build's on a log shot.

- **T29. A transition is a track item.** `GetItemListInTrack` returns each dissolve as an item of its own, named "Cross Dissolve", with no media pool clip and False for every transform property. Raw item numbers after a dissolve are one higher than the manifest's span numbers, so an effect applied on `span_index + 1` of the raw list landed on the wrong item. Measured 2026-11-10 on a 48-span build with three dissolves: 51 items, and the outro's words belonged on items 45 to 51, not 42 to 48. `api.clip_items` is the one count: items with a media pool clip only, so transitions are skipped, and so are titles, generators and compound clips, which have no media pool item either. `vertical_apply` and `apply_effect` both number items with it, so `items` is a clip number from 1 and `span_index + 1` is right again; `apply_effect` also takes `spans` (the manifest's own indices, from 0) and records the raw track position in each target row. A transition item is never a target, so it cannot reach `AddFusionComp`. `timeline_items` lists the raw track, dissolves included: its `index` is the raw position and its `clip` is the clip number `items` takes (null for a dissolve). `apply_grade`, `stabilize` and `reframe_apply` still take raw positions. Live-tested 2026-11-11 on a 51-item, 48-clip build with three 2-frame dissolves (raw 23, 30 and 37): clip n is raw n up to the first dissolve, raw n + 1 after it, n + 2 after the second, n + 3 after the third. `apply_effect` with `spans` and with `items` for the same clips returned the same `plan_sha`, so the two spellings are one plan. Clip numbers run per track (the first clip on V2 is clip 1). A clip number past the clip count is refused with the counts ("no clip(s) [49, 51] on V1 (48 clip(s) in 51 item(s); ...)"), so a raw position is not a valid clip number. A dissolve imported from FCPXML is the same kind of item (centred on the cut, any length). Not tested live: a title, generator or compound clip. The code skips it as it skips a dissolve (`is_clip` is a media pool lookup). Until 2026-11-11 the plan did not name it. Now `apply_effect` and `vertical_apply` return a `skipped` list (raw position, name, reason) for every item they leave out and the dry run's summary counts them, so a title or generator on the track shows up in the plan. Count the `skipped` rows against the dissolves you expect before trusting an `items` list on a timeline a person has edited; `timeline_items` shows the same items as null-`clip` rows. A live check of the list on a real title or generator by the operator follows. An offline clip is believed to keep its media pool item, so it is counted and not reported in `skipped` (believed, not live-tested; nothing here detects offline). `reason` is one fixed text for every row, because the item API this module uses gives no kind: a dissolve, title, generator and compound clip read alike, and `name` is the clue. The two refusals a skipped title or generator most often causes, a clip number past the count in `apply_effect` and a crops.json count mismatch in `vertical_apply`, name the skipped items by track and raw position. `vertical_apply` has skipped transition items since 2026-11-10 (before that it refused any timeline with a dissolve); `apply_effect` counted raw items until the same day.
- **T32. A draft's window is one frame late.** The draft farm composes a `scale-window` or `crop-window` over its plate with an ffmpeg overlay or blend. Live-tested 2026-11-11 on a 5952x2646 HEVC source at 29.97 fps drawn at 24 fps (hardware and software encode alike): the window layer starts a frame after the plate. Frame 0 shows the plate alone, the window is on screen from frame 1, and the full-frame snap lands on frame 38 where the macro's is frame 37. A `crop-window` that follows another `crop-window` can show its incoming shot at full frame on its first frame. The cause was not found. Time a window or a snap from the build's `timeline_items` read-back, not from a draft (41 ms at 24 fps).
- **T35. The Fusion Magic Mask is a point tool, one subject a node, and its controls are not in pixels.** Run live 2026-11-11 ([recipe](fusion-macros.md#person-matte-the-magic-mask-recipe)). The Fusion page's node (`comp:AddTool('MagicMask', ...)`) has no Person or Features mode: each click is a point, one click segments one region (a jacket, not the person), and it takes four or so clicks and a wait of about 6 s each to tint a whole person. Tracking both ways over 178 frames took about 16 s and followed one subject cleanly; a second person clicked in the same node survived only on the stroke frame. A tool added by script while a node is selected splices itself into that node's output (here `Merge2 > MediaOut1`), so read every link back. Matte Blur is not pixels (3.0 gave a halo of about 40 px at 1080p; 0.3 left a rim of a few), and Erode/Dilate 0.3 grew the matte over most of the frame, so leave it at 0. `OUTPUT_Name` is nil on an output; use its `Name`. One run, one handheld clip.
- **T34. 9:16 window comps opened off the crop centre on a render.** `scale-window` and `crop-window` are centred on the source frame, and `vertical_apply` left them there (`unmoved_comps`) when this was rendered. Rendered 2026-11-11 on a 9:16 copy of a 7-item montage with one window of each kind, the windows opened off the crop centre, by amounts the macro definitions alone did not predict. The `scale-window` box (a render frame is 1080x1920) opened low and to the right: top and bottom at 844 and 1266, centre about 95 px below the frame centre, left edge at x 496, its right edge clipped by the frame edge, so its centre was at least 248 px right of the middle and the incoming subject's head was cut off. The `crop-window` showed nothing for its first five frames, then a strip glued to the left frame edge, its right edge at x 24 at frame 5 and 216 for a ten-frame hold, centred vertically and about 430 px left of the middle, before it opened to full frame by its frame 25. The plates held: the outgoing shot kept its framing across both cuts (about 1 px and 0.1 percent in scale at one cut, inside the shot's own frame-to-frame jitter at the other, measured outside the window box against consecutive in-shot pairs). Judge a moving shot against that baseline, not by an unshifted pixel difference. The `scale-window` ended its last plate frame at 71 percent of the frame height and the next frame was the whole incoming shot (mean luma change 23 against 1 to 5 inside a shot; a third of the pixels changed by more than 25 levels). That matches the macro's own keys (Size 0.72 at frame 36, then the one-frame snap to 1.0), so the pop is the designed snap and not a fault of the render; whether it is wanted on a 9:16 edit is a taste call. The `crop-window` ended at 98 percent of the height and its snap changed the frame by 5, and its last growth step by 11. Cause: comp space is the whole 16:9 source frame and the item's Pan shifts the comp's output (T15), so a window drawn at source x 0.5 lands (0.5 - cx) x the source's width in output pixels away from the crop centre. A 4:3 source filled to 1080x1920 is 2560 px wide, so a crop centre of 0.4 puts a window centred at 0.5 about 256 px right of the middle, which agrees with the measured "at least 248 px right"; the `crop-window` has the same cause (its `Rectangle1` is centred at 0.5), but its measured 430 px left was not reconciled with a crop centre. The `scale-window`'s 95 px below the middle is consistent with the macro's own first Y key (0.45, 0.05 of 1920 px), which is by design. Fix (the Pivot rule below was measured live 2026-11-12: a Transform at Size 0.5, Pivot 0.4, Center 0.5 on a crop-centre-0.4 item put the box's left edge about 28 px in, as predicted, against about 284 px for the other rule; the window itself is not yet re-checked on a render): `vertical_apply` sets a `crop-window`'s `Rectangle1.Center` to (cx, 0.5), and a `scale-window`'s `Transform1.Pivot` to (cx, 0.5) and nothing else. Pivot is the anchor of the scaling, not a shift of the picture at Size 1, so the content at the crop centre stays at the crop centre through the window and across the snap to full frame; the box sits within about s * (0.5 - cx) of the source width off the crop centre ([At 9:16](fusion-macros.md#at-916)). A rendered window, started by the operator, comes later; until then look at the first and last plate frame of every window on a 9:16 build before delivery. One render, two windows, a close-up and a wide shot; the hand-set crop centres were synthetic, so this is a plumbing check. Not measured: the window's size curve against the design, the content colour, audio.

## Framing

- **T6. Pan units.** Pan is measured against the fitted picture, the source scaled to the timeline by its input scaling before the item's zoom: Pan = shift x timeline width / fitted picture width, the shift being how far the picture moves in output pixels with the item's zoom already in it. Tilt is the same on the height with the opposite sign: the shift is measured y down and Resolve's Tilt is y up. Where the fitted picture spans the timeline (a 16:9 source on a 16:9 timeline) Pan is plain output pixels. `reframe.resolve_props` writes it this way, and for a 9:16 fill it comes to T15's (0.5 - crop centre) x 1080 x item zoom. An earlier wording multiplied by the item zoom beside a "scaled image width"; read as the fitted width that is an extra factor, which the code does not have (it cancels if the width is the zoomed one).
- **T7. Pan moves the Fusion output too.** At 16:9 a zoom's pivot and a title's merge centre go on the crop centre: 0.5 + (crop_x - 0.5) x (1 - timeline width / scaled width). Checked only in part: `reframe_apply` (16:9) writes Pan and moves no Fusion comp; it warns per item when it writes a Pan onto an item that has a comp (`GetFusionCompNameList`), and the formula is applied by hand. `vertical_apply` moves the `rp-fx` comps itself (T15). No code computes or reads back the 16:9 formula.
- **T15. 9:16 with fill.** Pan = (0.5 - crop centre) x 1080 x item zoom, written with the 9:16 timeline current (T27). Fusion comp space is the whole source frame, so a zoom pivot and a title centre sit at the crop centre itself. A title sized 0.14 at 16:9 becomes 0.048 at 9:16 for a seven-letter word. An earlier wording said that fills about 80 percent of the width; that was wrong. Live-tested 2026-11-11: a six-letter capital word in Arial Bold, refitted to 0.056, spans about 41 percent of the 9:16 frame (440 of 1080 px), because Size is a fraction of the comp's height and the width follows the letters and the font. Whether the constant should change is a decision, not a measurement. A word that pops from 60 percent to full over five frames must be judged on a late frame. A `person-matte-text` word moves the same way (`Text1.Center` x on the crop centre, size refitted), but its matte stays on the subject: the matte is a position in the source frame, and the crop does not move the subject. Pan units, live-tested 2026-11-11 on rendered frames of two 4:3 sources at zoom 1: crop centres asked at 0.36 and 0.68 template-matched at 0.3602 and 0.6797, where a reading of Pan as literal output pixels would have landed near 0.38 and 0.65. A zoomed item (1.3, 1.5), an edge-clamped item and a BRAW item read back exactly (0.5 - cx) x 1080 x zoom, and the offline preview's crop box and the applied Pan agree on every centre to 0.0001 by that arithmetic; Live-tested 2026-11-11 on rendered frames of a five-item 9:16 build, matching each frame against its source (the render is graded and the preview is flat, so edges were matched, not pixels): the window centre landed on the planned centre to under 0.1 px at 540 px wide on a zoomed 1.3 item (0.3000), an edge-clamped item (0.2109, no black: no pixel under luma 5 on the clamped edge), a zoomed 1.5 and edge-clamped item (0.8594, no black) and a retimed 0.5 item (0.4000, with source time advancing at half speed as built). A BRAW item (0.7000) matched on one frame only, against a Resolve frame (`get_image`, source `media_pool_clip`, T33) because ffmpeg cannot decode BRAW; a second, independent measurement did not cover it. The offline preview drew the same centres within about 0.6 px on the four items it can draw. Vertical position was not exercised (Tilt 0 on every item), nor was a zoom below 1 or a hand-edited centre outside the clamp.
- **T16. The face planner picks the face it can track.** That can be a bystander at the frame edge, a child included. Read every crop on a sheet before applying it. On one eight-video run, nine crops of 120 needed a hand-set centre.
- **T27. Pan and Tilt follow the current timeline.** `GetProperty` and `SetProperty` express an item's Pan and Tilt in the pixels of whichever timeline is current, not the timeline the item sits on. Measured 2026-11-10: one item on a 1080x1920 timeline read Pan -378.0 with a 3840-wide timeline current and -106.3125 with its own timeline current (ratio 1080/3840). A pan written under the wrong timeline lands at that ratio of the shift asked for, and a read-back taken in the same state passes. Make the item's timeline current before writing or reading framing, and prove a crop on a rendered frame (T26). `vertical apply`, `reframe_apply` and the `cut` aspect build do this since 2026-11-10. A Pan read through `timeline_items` also follows whichever timeline is current, so a read taken while another 1080-wide timeline is current looks right either way and proves nothing. Not tested live (2026-11-11): no tool makes a chosen timeline current (T33), so the discriminating read, a 16:9 timeline current while a 9:16 one is read, was not made, and the only read-back that counts is the write-time one the build tools take with the target current. A render on 2026-11-11 is consistent with that write-time read: the applied Pans put every window centre on its planned value to under 0.1 px (T15), where a 1080/3840 error would have shown as a framing jump.
- **T31. BRAW has no 9:16 preview.** ffmpeg has no BRAW decoder, so on a plan that holds a BRAW item `vertical plan` fails on its review sheet ("no decoder found"; `--no-sheet` skips the sheet), `vertical draft` fails on the item, and `vertical review` refuses without a `preview.mp4`, so `vertical_apply` refuses the plan as unreviewed. Live-tested 2026-11-11 on a 6048x4032 BRAW clip. Leaving the BRAW item out of the plan does not help, since `vertical_apply` refuses an item count that differs from the track. The probe that got past the gate set `reviewed` by hand in a scratch copy of `crops.json`, on a sandbox timeline; do that only after the operator has seen a frame of the BRAW item (`get_image` with source `media_pool_clip`, T33). Whether a linked proxy can be drawn instead was not tested. The preview also draws a retimed item at real speed (`crops.json` carries no speed), so it shows more of the source than the build plays; its framing is right, since a retime does not change Pan (live-tested 2026-11-11: the rendered retimed item matched its source at half speed, correlation 0.96 against 0.5 at real speed). Do not compare preview and render frame for frame on a 59.94 fps source: Resolve and ffmpeg pick different source frames for a 24 fps timeline, and handheld motion between them read as offsets of a few to 16 px that were not a framing difference. Match each frame against its source instead; on the two 59.94 fps items the direct comparison scattered, on the 29.97 fps items it agreed to under 1 px.

## Color and Camera Raw

- **T19. A grade travels as a `.drx`.** `Timeline.GrabStill()`, then `GalleryStillAlbum.ExportStills([still], folder, prefix, "drx")` writes `<prefix>_1.1.1.drx`. `Graph.ApplyGradeFromDRX(path, 0)` on another item returned True and the item's CDL read back identical. The call replaces the item's whole graph. Not tested: whether windows, a tracked mask or noise reduction survive the trip.
- **T20. BRAW decode.** A BRAW clip's properties expose `ISO`, `White Point (Kelvin)`, `White Balance Tint`, `Input Color Space` and `Input Gamma`. No property names Decode Using. Setting it to Clip stays a computer-use step.
- **T21. Magic Mask needs a stroke.** `TimelineItem.CreateMagicMask("F")` returned False at once on an item nobody had drawn on. A person matte made outside Resolve ([cutout](reel.md)) needs no click.
- **T30. An untagged clip follows the project setting.** In a colour-managed project a clip with no Input Color Space tag reads Input Color Space "Project" and Data Level "Auto" (live-tested 2026-11-11 on a derived 720p ProRes file imported by `assemble_timeline`). "Project" means the clip follows the project's input colour space setting. This entry first said such a clip reads a Rec.709 space; that was wrong, and what the setting decodes as was not read. A V-Log file left that way renders in log, flat and grey, and no read-back catches it, because the clip's tag reads back exactly as it was left. `deliver_check` has a `log_flat` row for the render: five sampled frames that never reach near black or near white FAIL it, whatever the tags say (a heuristic; a flat look on purpose fails too). Measured 2026-11-10: a render pair of V-Log footage came out in log before anyone looked. A log source needs its Input Color Space set before it is graded or rendered; `ingest` does that for its own imports from what `detect` found. `assemble_timeline` now does the same for the files it imports itself (Input Color Space and Data Level, written and read back, on a colour-managed project only), lists in its dry run what `detect` says and what a clip already in its `methods [auto]` bin reads. It tags a clip it imports, a file that also sits in another bin included (the run imports its own copy, which is the clip that renders), and never rewrites a clip that was in the pool before the run, checked by clip id: one that is log by `detect` and reads Rec.709 is a problem line, and the timeline is left in place. A source `detect` cannot pin gets a note and no tag; tag it by hand. A derived file (a render or an export, for example an ffmpeg-made ProRes or H.265 file) is never tagged: `ingest` skips it ("derived file (render or export)") and `assemble_timeline` imports it with action `none` and a note, and it reads "Project" and "Auto" afterwards. The dry run lists its detected Data Level as Video anyway; for a file with action `none` that is `detect`'s proposal, not what is written. Whether a clip left at "Project" trips the problem line above (written for a Rec.709 read) was not tested. Data Level accepts "Full" and "Video" and reads each back exactly (live-tested 2026-11-11: a V-Log clip tagged Full, an Apple Log clip tagged Video, each read from the media pool). `ingest` and `assemble_timeline` write the value `detect` proposes (Full for V-Log, Video for Apple Log); neither lets the caller choose another, so Data Level was shown on two clips and not flipped on one. A log clip tagged before Data Level was written reads the right Input Color Space with Data Level "Auto". A frame of a tagged V-Log clip drawn from the media pool (T33) came out graded, not flat log; no untagged V-Log clip existed to compare it with. The look is a second half of the same rule. The draft farm draws with a camera cube (`<look> [<camera>].cube`), while a colour-managed build takes the look's `[RCM]` cube; the two are not interchangeable, and one edit uses one camera profile.

## Delivery

- **T17. A music montage has no captions.** A destination that wants captions (sidecar or burn-in) refuses a timeline with none. `social_9x16` alone carries a 29.97 fps floor (`min_fps` 30000/1001 in `resolve-config.json`): a lower rate gets a `deliver_check` WARN and a `queue_render` plan warning, never a refusal. `social_9x16_music` has no captions and no floor. Use `social_9x16_music`, or queue a master at 1080x1920 and transcode it: libx264 crf 16 preset slow, yuv420p, AAC 320k, two-pass loudnorm to -14 LUFS (`delivercheck.loudnorm_filter`), `+faststart`. Tag colour with `-x264-params colorprim=bt709:transfer=bt709:colormatrix=bt709`; the `-color_primaries` and `-color_trc` output flags left both unknown.
